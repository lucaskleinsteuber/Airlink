# AirLink 0.3 additions — protocol 1

Additive fields: Device.canRelay=false for old/new devices until explicit host grant. Settings adds sendLimitBytesPerSecond/receiveLimitBytesPerSecond (int64,0=unlimited; otherwise1024..1TiB/s) and shortcut `{enabled,keyCode,modifiers}` using Carbon keyCode/modifier bits; migrated settings default Shift+Command+L (keyCode37,modifiers768), enabled. Explicit disabled setting stays disabled. Limits apply globally per direction to payload I/O (normal transfers, public shares, relay); default unlimited. No content/clipboard changes.

Status adds currentDeviceId (guest pairing id,host localid), relayDevices (other online authorized browser peers, only shown to relay-enabled browsers), relays (host all; guest only participant), statistics (scope to host or guest). Names/IDs only, no peer addresses/credentials. A sender requires canRelay+canSend, receiver canRelay+canReceive. Changing permissions/revoking cancels affected relay activity. Recipient must explicitly accept every new relay offer.

## Browser relay

A local desktop service brokers bounded RAM chunks, never stores a complete payload or received relay file. Metadata/checkpoints survive restart, RAM data doesn't. Both browser tabs must stay open; source files must be reselected after losing access. Source computes each file's full SHA256 in its existing worker before creating the offer; selected originals stay unchanged. 8MiB chunks carry SHA256, final normal full download checks full digest before final bytes are released. Partial-range retries validate each block and source identity; no false saved/verified-client completion claim.

- `POST /api/v1/relays` RelayCreate `{receiverId,files:[{id,path,size,modified,directory,sha256}]}` -> Relay (offered). File SHA256 required for non-directory, including empty file hash. Immutable manifest. Browser sender can choose host (existing transfers API) or another authorized browser (relay API).
- `GET /api/v1/relays/{id}` -> participant Relay.
- `POST /api/v1/relays/{id}/accept` -> Relay, receiver only; state ready. `pause|resume|cancel` either participant. Resume cannot skip acceptance. Host IPC `relay.accept|pause|resume|cancel {id}` administrative only; accept requires explicit receiver action, host may pause/cancel but must not autoaccept for a guest.
- `GET /api/v1/relays/{id}/request` -> `{request:RelayRequest|null}`, sender only. Short/long polling; no changes when idle. Request identifies requested file/chunk and an unpredictable per-request ID. Source must refresh state, use same verified sources, and retry network errors without pushing unsolicited chunks.
- `PUT /api/v1/relays/{id}/files/{fileId}/chunks/{index}?requestId=...` -> `{delivered:true}` after that RAM block is consumed by the receiver transport. Raw8MiB (short final); header X-Chunk-SHA256. Source only. Reject wrong/stale request and changed confirmed chunk hash. Handler can wait for receiver consumption; pause/cancel/revoke/disconnect interrupts it. Retry based on fresh request, never assume a lost ACK means confirmed download.
- `GET|HEAD /api/v1/relays/{id}/files/{fileId}/download` receiver only, after explicit acceptance. Stable ETag and single HTTP Range supported. HEAD/invalid ranges don't ask the source for bytes or claim progress. At most2 active relay file streams globally; bounded chunk buffers. Receiver must use browser download manager; display transport delivery, not saved-file verification. Paths/empty directories preserved via streamed ZIP64 `/archive` fallback with no archive resume promise.

States offered,ready,queued,running,paused,reconnecting,delivered,failed,cancelled. Delivered means the host handed all byte ranges to the receiver transport; it is not an integrity attestation from the client filesystem. A relay interrupted by host/tab/network restart reconnects when both sides return; receiver may need to resume its browser download/restart archive. Last confirmed metadata alone cannot deliver bytes without source access. Never silently turn relay into a stored host upload.

## History and statistics

Local IPC `history.list {query?,state?,direction?,deviceId?,limit?}` -> History `{transfers,relays}`; defaults limit100,max500. Search case-insensitive file names/device names; newest first. Direction send/receive/relay. `history.clear` clears only terminal metadata (completed,failed,cancelled,delivered), never payload files, originals, shares, clipboard or active transfers. Statistics describe the remaining history; traffic payload counters remain lifetime counters.

Authenticated `GET /api/v1/history?query=&state=&direction=&deviceId=&limit=` returns only owned transfers/participant relays. `DELETE /api/v1/history` removes only this device's terminal history association; must not remove another participant's relay history. Host localclear can clear all terminal records. Guest stats never contain other devices' names/data or host-wide traffic counters.

Statistics fields in model: confirmed sent/received transfer bytes, completed/failed/cancelled/active counts, unique relayed transport bytes/deliveries, history cohorts grouped by last-activity date in UTC (not per-day wire accounting), host-only lifetime payload traffic counters. Relay bytes are separate from verified completed files. Zero-copy relay metadata contributes via model.Relay; no duplicated transfer entries for the same relay. Browser download initiation must still not count as verified completed transfer.
